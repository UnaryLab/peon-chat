# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An always-on Slack multi-agent framework: one Python process runs several Slack bots, each its own Slack app, each backed by a CLI (`claude` or `codex`). Current agents (defined in `agents.json`):

- **Aristotle**: claude, `unarylab-research:research_manager`
- **Brunel**: claude, `unarylab-research:project_manager`
- **Cicero**: claude, general (no sub-agent)
- **Dijkstra**: codex, `project_manager` codex profile (from the unarylab-codex-marketplace, installed into `~/.codex`)

See `README.md` for installation and Slack usage, and `ARCHITECTURE.md` for the full internals (code layout, the backend abstraction, the verified CLI invocations, the session store, and hot-reload reconcile mechanics).

## Commands

Everything runs in the `peon-chat` conda env (Python 3.12):

- Run all bots (always-on): `conda run -n peon-chat python -m src`
- Full test suite: `conda run -n peon-chat python -m pytest tests/ -q` (mocked/offline, no live Slack or CLI calls)
- Single test: `conda run -n peon-chat python -m pytest tests/test_build_command.py::<test_name> -q` (tests are split into themed `tests/test_*.py` files sharing `tests/helpers.py`)
- Lint / format: `conda run -n peon-chat ruff check src tests` / `ruff format src tests`
- Print a Slack app manifest: `python -m src manifest <name>` (add `--write` to dump `manifests/manifest-<name>.json`)

## Architecture (the parts that span files)

**Config is split on purpose.**
- `agents.json` is the single source of truth for agent *definitions* (`name`, `display_name`, `backend`, `model`/`effort`, plus `claude_agent` on claude entries only, and `codex_profile` on codex entries only). `codex_profile` is the optional codex-only persona analog of `claude_agent`: the NAME of an operator-installed `~/.codex/<name>.config.toml` profile (whose `developer_instructions` is the persona), which `codex_runner` applies as `--profile <name>` on the fresh run since `codex exec` has no agent flag (model/effort still come from `agents.json` via the CLI flags). `src/agents.py` loads it into `REGISTRY`; entries with duplicate `name`s are rejected at load (ValueError), since the name keys the stores, tokens, and live handler set.
- `.env` is *authoritative* runtime config (secrets, the single `AGENT_TIMEOUT_MIN` timeout (minutes, default 2880, `0` disables; one knob for both runners' subprocess deadline AND a background job's max lifetime; name and default single-sourced in `common.agent_timeout_min`; a malformed value logs a warning and falls back to the default via `_int_env` in `common.py`, never killing the process at import), `SESSIONS_PATH`, and the feature toggles below; NOT model/effort, which live only in `agents.json`). `src/env.py`'s `load_env()` runs with `override=True` as the FIRST executable code in `src/__main__.py`, before anything reads the environment. That ordering is why `.env` beats shell variables and why import-time reads pick it up. Because `load_env()` populates `os.environ` and the runners spawn the CLI with no explicit `env=`, EVERY var in `.env` is inherited by the `claude`/`codex` subprocess (and any skill it runs). So a var a skill expects from the shell but that launchd/systemd do NOT inherit (e.g. `OBSIDIAN_VAULT_PATH` for the `obsidian-*` skills) belongs in `.env`, NOT hardcoded into the OS-specific `deploy/` plist/`.service` templates.
- **Feature env vars** (all optional, all read LIVE per call so a SIGHUP `.env` reload toggles them; `WORKDIR_BASE` and `JOB_MAX_CONCURRENT` are documented in `.env.example`, while `SHOW_USAGE`/`STREAM_OUTPUT` default ON in code and are deliberately NOT listed there, added to `.env` only to disable): `SHOW_USAGE` (default ON: append the usage/cost/context-% footer), `STREAM_OUTPUT` (default ON: incremental streaming; `0` forces the byte-identical legacy argv), `WORKDIR_BASE` (base dir for the per-thread workdir, default `~/Projects/.peon-chat-workdirs`, an absolute path OUTSIDE the repo so a run's default cwd is never the framework source; set `WORKDIR_BASE` to override), `JOB_MAX_CONCURRENT` (default 16: max background jobs running at once, GLOBAL across all agents, counting ALL persisted `jobs.json` entries, running or awaiting delivery, so a parked not-live-agent entry holds a slot; `0` disables; an at-limit `<<job:>>`/`<<spawn:>>` start is DECLINED with a note, never queued). `AGENT_TIMEOUT_MIN` (above) is the exception on read timing: the runners read it ONCE at import (a change needs a restart), and the job watcher captures it live when a job's watcher (re)starts (so a reload applies to jobs spawned/re-attached after it).

**One process, one Slack app per agent.** `src/app.py` (a facade over `src/slack/`) builds one Bolt `App` + `SocketModeHandler` per *startable* agent (both `SLACK_BOT_TOKEN_<NAME>` and `SLACK_APP_TOKEN_<NAME>` present), each on its own thread. Agents missing tokens are skipped with a warning (partial startup). Each app dispatches to its own fixed agent; there is no keyword routing.

**Message handling is dedup'd and async.** A Slack event can arrive as BOTH an `app_mention` and a `message.*`, so the handler calls `seen_before("<agent name>:<event id>")` (an in-process bounded dedup, defined in `src/runners/common.py` and re-exported by the `claude_runner` facade). The key is PER AGENT (the Slack event id is identical across every agent's delivery of one message), so two agents mentioned in one message BOTH answer while each agent still answers once. `on_message` skips a follow-up that OPENS with another user's mention (directed at that bot; mid-text mentions still count as a follow-up), lets the `file_share` subtype through (a message carrying an upload; every other subtype is ignored), and does NOT cache a failed `bot_user_id` lookup (the next event retries). The handler acks Slack immediately, fetches a bounded visible Slack-thread transcript (`conversations.replies`, paginated up to 6 pages of 200, keeping the NEWEST 50 prior messages) for context, posts a placeholder (a random `quotes.json` line, else "<name> is thinking..."), runs the slow CLI in a background thread, then `chat_update`s the placeholder with the reply, so Slack's ~3s ack deadline is never blocked. Replies are capped below Slack's 40,000-char `chat_update` limit (`_truncate_for_slack`, 39,000-char head + truncation note; the `<<files:>>` marker is parsed BEFORE the cap and the interrupted label/usage footer appended AFTER, so both survive). The transcript lets another agent read Slack-visible output in the same thread; it does not share hidden CLI session state. **1:1 DMs are message.im-only:** Slack dispatches NO `app_mention` in an `im` channel (mpim group DMs do get it), so `on_message` routes every im message straight to `_handle` BEFORE its thread/mention gates. `_handle` splits the CONVERSATION KEY from the POSTING TARGET: a top-level DM message is keyed by the DM CHANNEL id (ONE rolling conversation per DM, spanning messages and restarts; threads inside a DM keep the normal thread key), the key feeds every store/override/workdir/interrupt lookup, and every post translates the key via `_reply_thread_ts(key)` (ts-shaped key -> that thread; channel-id key -> flat, `thread_ts=None`, covering acks, the placeholder, control acks, `files_upload_v2`, and a cron fire whose stored `thread_ts` is a DM channel id; re-exported by the `app` facade). Flat DMs SKIP the transcript fetch (no thread to fetch; the rolling per-channel session carries the context).

**A per-turn preamble is prepended to every prompt.** `_run_and_update` (in `src/slack/handlers.py`) prepends, on EVERY turn (not just new threads), a preamble carrying: the agent's identity from `agent["display_name"]` (agents carry NO built-in name and the persona prompt does not assert one, so without it the CLI can misidentify, e.g. from a stray `CLAUDE.md` it can reach; every-turn injection lets a thread that already learned the wrong name self-correct), the opt-in `<<files: ...>>` delivery rule, and a THREE-TIER work policy (the turn's process exits when the reply completes, killing background subagents/tasks): quick work is answered in the FOREGROUND within the turn; a long-running TASK needing intelligence should PREFERABLY end the reply with `<<spawn: <full self-contained task prompt>>>` plus a short ack (a soft preference, not a hard rule; the spawn MAY not see the thread context -- only a forked claude spawn inherits it, fresh claude and all codex spawns get a FRESH session -- so the preamble demands the prompt be a COMPLETE BRIEF for a reader with zero context -- goal, parameters, file paths, and decisions restated, never 'above'/'as discussed' -- and peon-chat ALSO prepends the turn's Slack transcript to the spawn prompt as a safety net, see the spawn section); a long-running VERBATIM shell command the user wants run as-is ends the reply with `<<job: cmd>>` (zero-token, deterministic). Both markers: trailing line only, only when the work is genuinely long or the user asks for background work. This is a prompt-prepend (not `--append-system-prompt`) on purpose: ONE backend-agnostic seam covers both claude and codex without touching the load-bearing per-runner argv.

**Backend abstraction (`src/runners/`).** `get_runner(backend)` returns the `claude_runner` or `codex_runner` FACADE module (the Claude/Codex internals live in `src/runners/claude.py` / `codex.py`; the shared dedup `seen_before` and the run-cancel `Interrupt` token live in `src/runners/common.py`; codex does not import claude). The unified seam is `runner.answer(agent, prompt, prior_session_id, timeout=None, overrides=None, on_update=None, cancel=None, on_session=None) -> (reply_text, session_id, meta)`, so `app.py` is backend-agnostic: `get_session -> runner.answer -> set_session`. `meta` is `{context_pct, tokens, cost_usd, duration_s}` (any field `None`); `overrides` is the per-thread model/effort/workdir dict; `on_update(partial_text)` drives streaming; `cancel` is an optional `Interrupt` the worker passes so a `!stop` can SIGINT the streaming run (see Run interrupt below); `on_session(session_id)` lets the worker PERSIST the session id at run START (claude fires it the moment it mints a new id, BEFORE the subprocess, so an interrupted run stays resumable; codex accepts but ignores it). claude also self-heals a dead stored id: a `--resume` that fails with `No conversation found with session ID` clears the id and retries ONCE as a fresh session, so a stale id never wedges a thread (the marker is checked against the FULL stderr carried on the error object, not the 1000-char-truncated message).

**Per-thread JSON stores (vendor-neutral `src/store/`, re-exported by the `claude_runner` facade).** Four JSON stores (sessions/overrides/crons/jobs) share one lock (`_SESSIONS_LOCK`), one dir (`os.path.dirname(_sessions_path())` via `_sibling_store_path`), and `SESSIONS_PATH` redirects all four at once; they all sit beside `sessions.json`. `store/base.py` is the single source of truth for the lock + path resolution; `sessions.py`/`overrides.py`/`crons.py`/`jobs.py` are the per-store modules. `workdir.py` is a fifth store module but a path-only scheme under `WORKDIR_BASE` (it imports only `os`/`re`, and uses neither the lock, `_sibling_store_path`, nor `SESSIONS_PATH`). When a store fn is called with `path=None`, `store.base._resolve_path` resolves the path through the LIVE `claude_runner.<resolver>` (so a test's `setattr(claude_runner, "_sessions_path", ...)` still redirects every store), falling back to the local resolver. Dict-shaped stores use `_load_dict_store`/`_save_dict_store`; ALL FOUR stores write atomically (temp file + `os.replace`), so a hard kill mid-write can never leave a truncated store (which the tolerant loaders would read as empty, wiping sessions/overrides/crons/jobs):
- `sessions.json`: `(agent_name, thread_ts) -> session_id`. Claude stores a `--session-id` UUID (resumed via `--resume`); Codex captures and resumes its own `thread_id`. Each (agent, Slack thread) is its own conversation; context survives a restart. Used by BOTH backends (driven by `app.py`); not Claude-specific.
- `overrides.json`: `(agent_name, thread_ts) -> {model?, effort?}`, set by the `!model`/`!effort`/`!reset` control phrases.
- `crons.json`: a LIST of `{id, schedule, agent, channel, thread_ts, prompt, enabled}` (list-shaped, via base's shared `_load_list_store`/`_save_list_store`).
- `jobs.json`: a LIST of `{id, agent, channel, thread_ts, pid, logfile, cmd, started_ts}` background-job entries (list-shaped, same shared pair; `thread_ts` is the conversation KEY, so it may be a DM channel id). A SUBAGENT SPAWN entry adds `kind: "spawn"` (absent = legacy job; loaders tolerate old entries) and, for codex, the `lastmsg` file path; its `cmd` field holds the task prompt. A persisted entry means "still running, or result not yet delivered"; the completion watcher removes it only AFTER delivery.

**Telemetry footer (`SHOW_USAGE`).** When `SHOW_USAGE` is truthy, `app._format_usage(meta)` appends a one-line `· N% · X tok · $Y · Zs` footer (each field dropped when `None`). Default ON; read live so a SIGHUP `.env` reload toggles it.

**Streaming (`STREAM_OUTPUT`).** Default ON. Both runners read the CLI's JSONL stdout incrementally and call `on_update`; `app._make_stream_updater` throttles `chat_update` to ~1/sec, with an unconditional final update. Streaming runs drain stderr on a concurrent daemon thread (`drain_stderr` in `common.py`) so a CLI writing >~64KB of stderr can never deadlock the stdout readline loop; the drained text still feeds error messages. CLI output is decoded with `errors="replace"` on both paths (non-UTF8 bytes degrade instead of raising). `STREAM_OUTPUT=0` forces the legacy single-blob path whose argv is byte-identical to the pre-streaming code. Claude streaming argv adds `--output-format stream-json --include-partial-messages --verbose`; Codex argv is unchanged (it already emits `--json`).

**Control phrases (one dispatcher).** `app._handle_control_phrase` matches `CONTROL_RE` (`^!(model|effort|reset|new|cron|job)\b ...`, DOTALL so a multi-line phrase like a `!cron add` with a multi-line prompt still matches) on the de-mentioned prompt and dispatches; a handled phrase acks into the thread and does NOT run the agent. `!model`/`!effort`/`!reset` mutate `overrides.json`; `!new` clears the conversation's `sessions.json` key (fresh context next message; overrides/crons/workdir kept; declined while a run is in flight for the key, since the worker's end-of-run `set_session` would resurrect the cleared id); `!cron add|list|remove|on|off` mutates `crons.json`; `!job list|kill <id>` manages the DISPATCHING agent's background jobs AND subagent spawns (agent-scoped across ALL conversations: another agent's job id reads as "no such job"; `list` shows a spawn entry's task prompt prefixed `spawn:`; `kill` SIGTERMs the job's whole process group via `os.killpg` and never removes the `jobs.json` entry, since the watcher owns delivery + removal, so a kill settles through the normal completion flow). Interrupt phrases (`!stop`/bare `stop`/`ctrl-c`/`^c`/`interrupt`) are matched BEFORE the `!`-gate and signal the thread's in-flight run (see Run interrupt below).

**Run interrupt (`!stop`).** A `!stop` (or bare `stop`/`interrupt`/`ctrl-c`/`^c`) interrupts the run in flight for that `(agent, thread)` without starting a new one (matched BEFORE the `!`-gate, since bare forms carry no `!`). `src/runners/common.py`'s `Interrupt` token carries the live `Popen`, attached by the runner via `.arm(proc)`; `arm` and `.request()` share one lock, so a `!stop` sent BEFORE the subprocess spawned is delivered the moment it starts (no lost pre-spawn stop). `.request()` sets a flag and SIGINTs a live proc (mimics Ctrl-C, letting the CLI flush its session); if the proc already EXITED but its stdout is still open (an orphaned descendant holds the write end, so the reader never sees EOF), it closes the read end instead, unblocking the wedged reader, which settles as an interrupted partial. `src/slack/interrupt.py` is the in-memory `{(agent, thread): Interrupt}` registry, which doubles as the per-thread BUSY GUARD: `_handle` atomically claims the slot via `try_register` BEFORE spawning the worker, and a second message while a run is in flight is declined with a "still working" ack (never two runs `--resume`-ing one session concurrently); the decline also flags the token (`mark_pinged`), and the flagged run posts a short "finished, see the updated reply above" note as a NEW message when it settles (its real reply is an unnotified in-place edit of a placeholder the declined exchange buried); cron fires claim the slot the SAME way (`try_register` in `_run_and_update`) and a fire into a busy thread is SKIPPED (placeholder updated to a "skipped: a run is already in progress" note; the unconditional `register` remains only as the raw primitive). The worker passes the token as `runner.answer(..., cancel=token)` and `unregister`s it in a `finally`. On the SIGINT-induced nonzero exit the streaming loop checks `cancel.requested` and RETURNS the partial reply instead of raising, so `set_session` still persists the id and the thread stays resumable (the worker marks it `_(interrupted)_`). STREAMING ONLY: under `STREAM_OUTPUT=0` there is no `Popen` handle, so `!stop` is a no-op.

**SECURITY: agents run with full unsandboxed machine access.** Every run is fully unsandboxed: the runners emit `claude --permission-mode bypassPermissions` and `codex -s danger-full-access` (fresh) / `-c sandbox_mode=danger-full-access` (resume), and `_run_and_update` injects the per-thread `_workdir` (under `WORKDIR_BASE`, namespaced by agent+thread; default `~/Projects/.peon-chat-workdirs`, an absolute path OUTSIDE the repo) into `overrides` as the run's cwd. A run can read/write any absolute path and run any command; the `_workdir` is only its cwd/home so the outbound file-upload-back works, not a confinement boundary. Anyone who can DM/mention a bot can run arbitrary commands as the operator; this is a deliberate personal/lab tradeoff, so restrict who can reach the bots.

**Files in/out.** Inbound: `files[]` on a message (including a threaded follow-up with subtype `file_share`, the one subtype the handler lets through) are downloaded with the bot token (`_http_get_bytes`, urlopen with a 60s timeout so a stalled CDN read can't wedge the thread's busy slot) into a per-thread temp dir and their paths appended to the prompt. Outbound is OPT-IN and model-driven: a run delivers files ONLY by ENDING its reply with a `<<files: name1, name2>>` marker (recognized solely as a trailing marker; a mid-text mention of the syntax is plain prose; the per-turn prompt-prepend in `_run_and_update` tells the agent to emit it only when the user explicitly asks for a file). `_parse_file_marker` strips the marker from the posted reply, and `_maybe_upload_named` resolves each name INSIDE the thread's workdir (`_resolve_named_files` rejects paths that escape it) and uploads just those via `files_upload_v2`. No marker (the default) uploads nothing, so an ordinary reply never dumps the workdir back. Requires `files:read`/`files:write` scopes.

**Background jobs (`<<job:>>`, detached, survives restarts).** A run requests long/background work ONLY by ENDING its reply with a `<<job: <shell command>>>` marker (same trailing-only rule as `<<files:>>`; mid-text is prose; the per-turn preamble scopes `<<job:>>` to a long-running VERBATIM shell command the user wants run as-is, and gates both background markers on genuinely long-running work or an explicit ask). Unlike the tempered files body, the job body may contain `>>` (own regex pair in `src/slack/jobs.py`, DOTALL): the opener must START A LINE (`(?:^|\n)[ \t]*` in both the parse and strip regexes; a mid-line prose mention never anchors), parse anchors at the LAST line-start `<<job:` closing at the `>>` ending the reply, and the OPENER LINE discriminates: an opener line containing `>>` must be a single-line marker closing at the very end of the reply (so a line-start quoted example followed by prose ending in `>>` stays prose, never shell), while only an opener line with NO `>>` may span newlines (heredocs; the one limitation: a multi-line body whose FIRST line contains `>>` is prose, so put `>>` appends on a single-line marker or on later heredoc lines); the one carve-out is that the body may not contain another marker opener (`<<job:`/`<<files:`/`<<spawn:`). Deterministic marker order in `_run_and_update`: the SPAWN marker is parsed FIRST, then the JOB marker, then the FILES marker (all BEFORE the 39,000-char cap), so a reply ending `<<files: a>>` then `<<job: cmd>>` then `<<spawn: task>>` (spawn line LAST) triggers all three. After the final reply posts, `_start_job` (in `src/slack/jobs.py`) spawns `/bin/sh -c <cmd>` DETACHED (start_new_session, stdin devnull, stdout+stderr into `job-<id>.log` in the thread workdir; unsandboxed like every run), persists a `jobs.json` entry, and arms a daemon watcher (`_watch_job`: `proc.wait()` this lifetime, or a pid poll after re-attach). On completion `_finish_job` reads the log tail (`_JOB_LOG_TAIL_CHARS`), delivers the result by synthesizing a follow-up agent turn through the SAME `_run_and_update` seam a cron fire uses (placeholder + `try_register` busy guard; the thread's session resumes, so the agent summarizes in context), THEN removes the entry (a failed delivery keeps it for redelivery on the next restart); a BUSY thread gets the raw completion note (exit code + tail) as a plain message instead, never a silent skip; all posting translates the key via `_reply_thread_ts`. An interrupted (`!stop`) run never spawns its job. On startup, `_reattach_jobs` re-arms a watcher per persisted entry (agent gone from the registry: dropped with a warning; agent not live: left for a later restart; exit code after re-attach is unknown, and the `os.kill(pid, 0)` liveness probe accepts the pid-reuse race). `!job list`/`!job kill <id>` manage the agent's jobs (see Control phrases above; a kill settles through the watcher's completion flow). Two guardrails (env vars above, `0` disables either): `JOB_MAX_CONCURRENT` (read live per spawn) caps running jobs GLOBALLY across agents; the count-check + append are ONE critical section inside `store.add_job` (the shared store lock), the pid only exists after Popen so the spawn happens FIRST and a declined spawn's fresh process GROUP is SIGKILLed and reaped (never a bare `proc.kill()`, which would orphan a forked child; no entry, no watcher, a "job not started" note in the thread instead). `AGENT_TIMEOUT_MIN` (captured at watcher (re)start, enforced from the entry's `started_ts`, so a re-attached watcher enforces only the REMAINING window and an already-expired job dies on the first poll; an entry without `started_ts` is treated as started now) kills an expired job's process group (SIGTERM, `_JOB_KILL_GRACE_S` grace, SIGKILL) and delivers through the NORMAL completion flow with a "timed out after N min" label.

**Background subagent spawns (`<<spawn:>>`, detached, ride the job machinery).** The sibling `<<spawn: <task prompt>>>` marker carries a natural-language TASK, not shell (same anchoring rules as `<<job:>>`, own regex pair from the shared `_greedy_marker_res` factory in `src/slack/jobs.py`; the preamble PREFERS it for long tasks needing intelligence and demands a self-contained COMPLETE-BRIEF task prompt). Before the `_start_spawn` seam, `_run_and_update` prepends the turn's ALREADY-FETCHED Slack transcript to the task prompt (SKIPPED for a FORKED claude spawn, which already carries the conversation -- fork-vs-fresh decided in ONE place, `jobs._spawn_fork_session`; `_compose_spawn_prompt` in `src/slack/jobs.py` is the ONE place the composition template lives; capped at `_SPAWN_TRANSCRIPT_MAX_CHARS` = 16000 keeping the NEWEST tail behind a truncation note, since the prompt rides the CLI argv; the transcript sits MID-PROMPT so marker text inside it is inert; callers with NO transcript -- flat DMs skip the fetch, cron fires and completion deliveries have none -- spawn the task body alone; never re-fetched). `_start_spawn` builds a one-shot CLI run through the dispatching agent's OWN backend runner's `build_command` (claude: non-streaming `--output-format json`; with a stored thread session id it FORKS it via `--resume <thread id> --fork-session` -- verified against claude CLI 2.1.201: resume but write to a NEW CLI-minted id, original untouched -- so the subagent INHERITS the full hidden conversation state, the forked id NEVER stored in `sessions.json` and the thread's stored id unchanged (the spawn launches after the reply posts, so it forks a quiescent session); without one, fresh with a minted ephemeral `--session-id` uuid, equally never stored; codex: the verified fresh `codex exec` shape with the `-o` lastmsg file placed in the thread workdir, named `spawn-<id>.last`, so it survives a restart -- codex never forks), applying the thread's `overrides.json` model/effort like a normal run, and hands the argv to the SAME `_launch_detached` guts `_start_job` uses: detached process group, `job-<id>.log`, `jobs.json` entry (plus `kind: "spawn"` and codex's `lastmsg` via `store.add_job(extra=...)`), watcher, the shared `JOB_MAX_CONCURRENT` cap (one counter for jobs + spawns, same decline-with-note), the `AGENT_TIMEOUT_MIN` expiry kill (delivered with a "background subagent timed out" label), `!job list` (task shown prefixed `spawn:`) / `!job kill`, and `_reattach_jobs`. Completion differs only in result extraction: `_spawn_result` reads the subagent's final message (codex: the `lastmsg` file; claude: the LAST JSON line in the log carrying a string `result`), falling back to the raw log tail on any failure and capping the result head+tail at `_SPAWN_RESULT_MAX_CHARS` (8000), and `_finish_job` delivers it with a `[background subagent finished/timed out ...]` head. NESTED-MARKER GUARD: the extracted result rides the delivery turn's PROMPT (or the busy-thread plain note) as DATA, and prompts are never marker-parsed, so a `<<files:>>`/`<<job:>>`/`<<spawn:>>` inside the subagent's output can never itself trigger an upload/job/spawn; only the delivering agent's OWN reply goes through normal marker parsing. An interrupted (`!stop`) run never spawns.

**Cron (Slack-native, in-process).** A daemon thread (`_scheduler_loop`) evaluates each minute once, sleeping to the NEXT minute boundary (not a fixed 60s, so the wake time never drifts into skipping a minute), re-reads `crons.json`, and fires each enabled entry whose 5-field expression (`cron_matches`, a hand-rolled matcher, no dependency; `N/S` steps use Vixie semantics, e.g. minute `5/15` = 5,20,35,50) matches the current minute. Each fire runs on its OWN daemon thread (`_scheduler_tick` spawns one per fire, so a long cron run never blocks the tick loop), synthesizing a run through the same `_run_and_update` seam; a fire into a thread with a run in flight is skipped via the `try_register` busy guard (see Run interrupt above). This is distinct from Claude Code's own `/schedule` (cloud routines).

**Model/effort source:** each agent's `model` and `effort` come SOLELY from its `agents.json` entry (the single source of truth, set on every shipped entry). There is no env-var override. `agents.resolve` reads the field and, only if it is missing/empty, applies a single code-level fallback (logging a warning): claude model falls back to the pin `claude-opus-4-8[1m]`, everything else to omit. Claude always emits `--model`; effort and the Codex model are omitted when their field is absent.

**Manifests are generated** from `agents.json` by `src/manifest.py`; `manifests/` is gitignored, not a source of truth.

## Things that bite

- **Three module paths are FACADES; keep the re-exports complete.** `src/runners/claude_runner.py` (re-exports `src/runners/claude.py` + `common.{seen_before, Interrupt}` + the whole `src/store/*` surface), `src/runners/codex_runner.py` (re-exports `src/runners/codex.py`), and `src/app.py` (re-exports `src/slack/*`) exist BECAUSE the test suite references symbols and monkeypatches attributes on these EXACT paths, and `get_runner` returns these objects (`get_runner("claude") is claude_runner`). So: keep `subprocess` (runner facades AND the app facade, where the detached job spawn is patched) and `tempfile`/`runners` (app facade) exposed as facade attributes (Kind-A shared-singleton patch targets); the Kind-B names (`_run_and_update`, `_scheduler_tick`, `_fire_cron`, `build_app_for`, `SocketModeHandler`, `reconcile`, `_attachments_dir`, `_http_get_bytes`, `_reply_thread_ts`, and the job/spawn seams `_start_job`/`_start_spawn`/`_watch_job`/`_finish_job`/`_pid_alive`) are resolved by their cross-module callers THROUGH the facade via a lazy in-body `from src import app as _appfacade`, and the store-path resolvers are resolved through `claude_runner` via `store.base._resolve_path`. When you add a symbol to a store/slack/runner submodule that a test references on one of these paths, re-export it from the relevant facade.
- **Adding an agent: reload or restart.** Flow: add an entry to `agents.json`, run `python -m src manifest <name>`, create the Slack app *From a manifest* (enable Socket Mode, get the token pair), add `SLACK_BOT_TOKEN_<NAME>`/`SLACK_APP_TOKEN_<NAME>` to `.env`, then either **hot-reload** (`kill -HUP <pid>`, or `systemctl reload`, which sends SIGHUP) or restart. In-flight conversations resume from `sessions.json` either way.
- **Hot-reload via SIGHUP (`src/app.py`, no restart).** `kill -HUP <pid>` (or `systemctl reload`) makes the running process re-read `agents.json` + `.env` and reconcile live connections by the **delta only**: added agents are connected, removed/now-unstartable ones are closed (`handler.close()`) and dropped, agents whose `agents.json` entry **or** resolved token changed are restarted, and **unchanged agents keep their live connection** (conversations are not interrupted). "Changed" is a per-agent snapshot of the entry + its two token values. Mechanism: the SIGHUP handler just sets a `threading.Event`; `main()`'s reload loop (which replaced the old `threading.Event().wait()` idle) does the reconcile on the main thread via `app.reconcile(live)`. **Crash-safe:** a missing/invalid `agents.json` or any reconcile error is logged and the running agents are left untouched (the process never dies). `agents.reload()` re-reads the registry and mutates `REGISTRY` in place. **Caveat:** finish editing BOTH `agents.json` and `.env` before sending the signal, since one SIGHUP reads both at once. POSIX only.
- **Runs as a service; CODE edits need a restart, not a reload.** SIGHUP only re-reads `agents.json` + `.env` and reconciles connections; it does NOT reload Python module code, so any change under `src/**` is invisible until the process is fully restarted. In this deployment peon-chat runs under macOS launchd (`~/Library/LaunchAgents/com.unarylab.peon-chat.plist`, logging to `peon-chat.log`); restart it with `launchctl kickstart -k gui/$(id -u)/com.unarylab.peon-chat` (systemd: `systemctl restart`).
- **The service `PATH` must include the CLI dirs.** The built argv uses the BARE binary name (`claude` / `codex`), both of which live in `~/.local/bin`. launchd's default `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`) omits that dir, so without an `EnvironmentVariables` > `PATH` key in the plist every run dies with `FileNotFoundError: [Errno 2] ... 'claude'`. Works from an interactive shell (which has `~/.local/bin`) but fails as a launchd/systemd service. The fix lives in the launch config, not the code (the test suite pins `argv[0] == "claude"`).
- **The built CLI invocations are load-bearing.** They were verified against the real CLIs; do not change the argv without re-verifying. Every run is fully unsandboxed, so `--permission-mode bypassPermissions` / `danger-full-access` are always present. Claude (non-stream = the asserted default path): `claude -p --output-format json {--session-id|--resume} <id> [--agent <x>] --permission-mode bypassPermissions --model <m> [--effort <e>] <prompt>` (the `--permission-mode` flag sits between `--agent` and `--model`, on BOTH fresh and resume). Codex: `codex exec [resume <tid>] --json --skip-git-repo-check {-s danger-full-access | -c sandbox_mode=danger-full-access} [--profile <p>] -o <lastmsg_file> [-m <m>] [-c model_reasoning_effort="<e>"] <prompt>` (Codex mints its own `thread_id`, which cannot be pre-set like Claude's session id; `--profile` is fresh-run only; `-s` on fresh, `-c sandbox_mode=` on resume). The `<<spawn:>>` FORK shape (claude spawns with a stored thread session ONLY): `claude -p --output-format json --resume <thread id> --fork-session [--agent <x>] --permission-mode bypassPermissions --model <m> [--effort <e>] <task>` (`--fork-session` verified against claude CLI 2.1.201, `claude --help`: "When resuming, create a new session ID instead of reusing the original (use with --resume or --continue)"; normal runs never pass it, so the default-path argv stays byte-identical). Verified flag values: `claude --help` lists `bypassPermissions` as a `--permission-mode` choice; `codex exec --help` lists `danger-full-access` as a `-s/--sandbox` value. **The one argv switch** (still byte-exact, asserted in lockstep): with `STREAM_OUTPUT` on (the run-time default), claude swaps `--output-format json` for `--output-format stream-json --include-partial-messages --verbose` (codex argv is unchanged, it already emits `--json`). The `STREAM_OUTPUT=0` path must stay byte-identical to the asserted default-path argv.
- **Tests are hermetic and offline.** A `conftest.py` autouse fixture pins `STREAM_OUTPUT="0"` (the legacy non-stream path) so the runner unit tests that mock `subprocess.run` assert the single-blob default-path argv deterministically, and `SHOW_USAGE="0"` so reply assertions stay footer-free (the footer defaults ON); streaming tests opt back in with `monkeypatch.setenv("STREAM_OUTPUT", "1")`. A second autouse fixture empties the interrupt/busy-guard registry between tests (a test that fakes the worker thread never runs the `finally` that frees the thread's busy slot). Model/effort need no env scrub: they come SOLELY from `agents.json` (no env-var layer), so a developer's shell cannot leak into the argv assertions. All subprocess and Slack I/O is mocked. The suite is split into themed `tests/test_*.py` files (by area: `test_build_command.py`, `test_stores.py`, `test_streaming.py`, etc.) that share cross-file constants/fakes from `tests/helpers.py`; put a fake used by one file in that file, a fake used by several in `helpers.py`.
- **Behavior-preserving changes must keep the default-path argv byte-identical** (the suite asserts exact argv). `.env` is never edited by tooling: change `.env.example` and have the user mirror it into `.env`.
- **Slack app reconfig for files, group DMs, and 1:1 DMs.** The file in/out feature needs the `files:read` and `files:write` bot scopes, group-DM support needs the `mpim:history` scope plus the `message.mpim` event, and 1:1 DMs need `features.app_home.messages_tab_enabled` (Slack's Messages Tab defaults OFF, which blocks composing DMs entirely with "Sending messages to this app has been turned off"; no scope involved). All are in the shipped `src/manifest.py`. After pulling any of these, regenerate each Slack app's manifest, update the app from it (or flip the setting by hand), and reinstall so scope additions take effect (the Messages Tab toggle applies without a reinstall).
